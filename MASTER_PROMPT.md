The target AgentDB product is a free, open-source embedded database where the AI

## 2. THE THREE-SURFACE ARCHITECTURE

AgentDB has three surfaces. They must be kept separate.

### A. AGENT SURFACE (MCP)
The target agent API is MCP. Phase 0 has 34 in-browser, MCP-shaped tool calls
and no MCP transport. Phase 1 targets a real MCP transport with 44 tools.
The agent does NOT write SQL. It calls MCP tools. The MCP layer translates
to the query engine internally.

### B. QUERY ENGINE (Semantic Surface)
The unified execution engine: SQL planner + vector ANN + BM25 scoring +
RRF fusion + memory recall. This is the only source of truth for data
operations. The MCP layer is a projection onto this.

### C. EXPLANATION SURFACE
Plain-English explanations generated from the query engine's execution plan
and the evidence ledger. Never hand-written. Never generated by a model at
explanation time. Template-based, deterministic, byte-for-byte reproducible.

**The invariant:** The MCP layer is a *notation* for the query engine. The
explanation is a *projection* of the evidence ledger. The query engine is
the only source of truth. If the MCP response and the explanation disagree,
the system is broken, not the agent.

## 3. WHAT "EXPLAINABLE" MEANS (Checked Property)

Explainability is not a doc comment. It is a mechanically checked property:

| Part | Definition | Enforcement |
|---|---|---|
| **E1. Completeness** | Every MCP tool call, every policy decision, and every data mutation has an explanation in the evidence ledger. | `evidence_append` is called automatically by the runtime after every tool execution. Missing entries are a runtime error. |
| **E2. Derivation** | The explanation is generated by the runtime from the execution plan + intent + decision. Never authored by hand. | The `audience_explanation` field in `evidence_ledger` is populated by the explanation generator, not by the agent. |
| **E3. Faithfulness** | The explanation is verified against the actual operation performed. Mechanism: template-based generation where slots are filled with typed values from the execution plan. | The explanation template for `execute_sql` includes the actual SQL, the row count, and the table name. If the template output does not match the execution result, it is a runtime error (AD-601). |
| **E4. Audience Fit** | The explanation is written for a named audience (engineer, auditor, end user, regulator) and meets a declared readability target. | Flesch-Kincaid grade ≤ 12 for auditor; ≤ 8 for end user. Max sentence length: 25 words. |

**What the system does NOT explain:** model internals, why a vector search
returned particular results, why a BM25 score was a particular value. The
explanation covers *what was done, why it was authorized, and by whom* — not
*why the algorithm produced that output*. Name this boundary explicitly.

## 5. NON-NEGOTIABLE DESIGN CONSTRAINTS (D1–D10)

Every item must be structurally unrepresentable to violate.

**D1. SINGLE FILE, ZERO DEPENDENCIES.**
The entire database is one file (`agentdb.db`). No external processes.
No Redis. No etcd. No MinIO. No config file (optional `agentdb.toml` for
advanced settings only). No port (MCP over stdio by default; optional HTTP
via `--http :3000`).
Enforcement: build system produces one binary. Integration test: copy the
file to a new machine, open it, verify data integrity.

**D2. MCP IS THE NATIVE API.**
MCP is not a plugin, not a separate process, not an adapter. The MCP server
is compiled into the binary. The Phase 1 target of 44 tools is the database's public API.
An agent that connects via MCP can do everything the database can do.
Enforcement: every data operation is reachable via an MCP tool. If an
operation requires writing raw SQL outside MCP, it is a design defect.

**D3. UNIFIED QUERY ENGINE.**
SQL, vector search, BM25 full-text, and memory recall are executed by ONE
query planner with ONE optimizer. Hybrid search (vector + BM25 + structured
filter + RRF fusion) is a single query, not three stitched results.
Enforcement: the query planner has a single cost model that includes vector
distance, BM25 score, and row-count estimates. No separate "vector engine"
process.

**D4. EVIDENCE LEDGER IS MANDATORY.**
Every data mutation (INSERT, UPDATE, DELETE, memory_store, memory_forget,
index creation, DDL) is logged to the evidence ledger. The ledger is
hash-chained, append-only, and immutable. No mutation occurs without a
ledger entry.
Enforcement: the WAL writes the ledger entry atomically with the data
mutation. A data change without a corresponding ledger entry is a crash
bug. `agentdb verify` checks chain integrity.

**D5. AGENT MEMORY IS A FIRST-CLASS PRIMITIVE.**
Memory is not a table the agent must manage. It is a language-level
primitive with: importance scoring, time decay, session scoping,
semantic recall (vector similarity over memory entries), and structured
filtering. `memory_store(key, value, embedding, metadata, ttl)` and
`memory_recall(query, top_k, filter)` are the API.
Enforcement: the memory API is in the core binary, not an extension.

**D6. STATELESS MCP (2026-07-28 SPEC).**
No session. No handshake. Every request carries `_meta` with protocol
version + client capabilities. `server/discover` is implemented. MRTR
(Multi Round-Trip Requests) is supported. Routing headers (`Mcp-Method`,
`Mcp-Name`) are present on all HTTP transport requests.
Enforcement: conformance test suite against the 2026-07-28 spec.

**D7. NO PHONE-HOME. NO TELEMETRY. NO LICENSE SERVER.**
The database does not call any external service. No analytics. No update
checks. No license validation. Works in air-gapped environments.
Enforcement: network audit of the binary. Zero outbound connections in
default mode.

**D8. APACHE 2.0. NO CLA. NO DUAL LICENSING.**
The code is Apache 2.0. No contributor license agreement. No patent grant
complexity. Enterprise can use it without legal review.
Enforcement: LICENSE file in repo. CI check: no non-Apache-2.0 dependencies
in the core binary.

**D9. THE AGENT NEVER WRITES RAW SQL (via MCP).**
The MCP tools abstract SQL. The agent calls `execute_query(filter, sort,
limit)` or `hybrid_search(query, filter, top_k)`, not
`"SELECT * FROM docs WHERE category='x' ORDER BY ..."`.
[NOTE: The `execute_sql` tool exists for advanced/debugging use but is
marked `dangerous: true` in the tool metadata and requires the `admin` role.
The default agent role is `read` or `write`.]
Enforcement: tool metadata includes `dangerous: true` + role requirement.

**D10. EXPLANATION IS A RUNTIME OBLIGATION.**
Every MCP tool call produces a one-sentence plain-English explanation that
is stored in the evidence ledger. The explanation is generated from
templates over typed values (the actual operation, the actual result, the
authorization decision). It is never hand-written, never model-generated,
never suppressible.
Enforcement: the explanation generator runs after every tool execution.
A tool call that completes without a ledger entry (including explanation)
is a runtime error (AD-601).

## 6. THE QUERY ENGINE

### 6.1 Storage
- **Primary format:** Single-file, B+Tree page-based (SQLite-compatible
  page format for the core tables). [Phase 3: full SQLite page format
  compatibility. Phase 1: simplified page format.]
- **WAL:** Write-Ahead Log for durability + crash recovery.
  A write lands in the WAL. Checkpoint folds WAL into the main file.
  Replay rebuilds from the (main file, WAL) pair.
- **MVCC:** Multi-Version Concurrency Control. Readers never block writers.
  `BEGIN CONCURRENT` for multiple concurrent writers.
- **Async I/O:** [Phase 4: io_uring on Linux, kqueue on macOS, IOCP on
  Windows. Phase 1: synchronous I/O is acceptable for the preview.]

### 6.2 SQL Layer
- Full SQL dialect: SELECT, INSERT, UPDATE, DELETE, JOIN, GROUP BY,
  HAVING, CTEs, window functions, subqueries, parameterized queries.
- JSON columns: first-class JSON type with path queries
  (`WHERE meta->>'category' = 'tech'`).
- Parser: `sqlparser-rs` crate [KNOWN: mature, active, MIT licensed].
- Optimizer: cost-based. Index selection (B+Tree, HNSW, BM25, bitmap).
  JOIN strategies (nested loop, hash, sort-merge). Aggregate pushdown.

### 6.3 Vector Search (Built-in, NOT an extension)
- `VECTOR(n)` column type (fixed-width float32).
- **HNSW** index (primary) + **IVF-PQ** for large-scale (10M+ vectors) [Phase 4].
- Distance metrics: cosine, L2, dot product, Hamming.
- **Hybrid search:** Combine vector + BM25 + structured filters in ONE query:
  ```sql
  SELECT * FROM docs
  WHERE metadata->>'category' = 'tech'
  ORDER BY vector_distance(embedding, $1)
  LIMIT 10;
  ```
- Quantization: scalar, product (PQ), binary [Phase 4].
- Target: < 10ms p99 for 1M vectors on a single core [Phase 4 benchmark].
- [Phase 1: feature-hash embeddings for the preview. Phase 2: pluggable
  neural embeddings (local ONNX or API).]

### 6.4 Full-Text Search (Built-in)
- **BM25** ranking with inverted index.
- Positional info for phrase queries.
- Stemming (English + pluggable).
- **Reciprocal Rank Fusion (RRF):** Automatic fusion of vector + BM25 scores
  in the query planner. Not a post-hoc merge.

### 6.5 Agent Memory (Built-in)
- `memory_store(key, value, embedding, metadata, ttl, importance)`
- `memory_recall(query, top_k, filter, session_scope)`
- `memory_forget(key)` / `memory_forget(filter)`
- **Importance scoring:** Each memory entry has an importance weight [0,1].
  Recall ranking = vector_similarity × importance × time_decay(age).
- **Time decay:** Configurable half-life. `decay_half_life = 7d` means a
  memory's effective importance halves every 7 days.
- **Session scoping:** Memories can be session-scoped (ephemeral) or
  persistent (survive restarts).
- **Cross-session:** Persistent memories are available across all sessions.

### 6.6 Change Data Capture (CDC)
- `CREATE STREAM my_stream ON table_name`
- Emits INSERT/UPDATE/DELETE events to: in-memory queue, file, or HTTP webhook.
- Agents can subscribe to data changes in real-time via the `stream_read` MCP tool.

### 6.7 Triggers & Functions
- SQL triggers (BEFORE/AFTER INSERT/UPDATE/DELETE).
- User-defined functions in Rust (compiled at runtime) [Phase 5].
- Python UDFs (optional, via embedded interpreter) [Phase 5].

## 8. THE EVIDENCE LEDGER

### 8.1 Schema
```sql
-- Tamper-evident, append-only. Hash-chained.
CREATE TABLE evidence_ledger (
  receipt_id     INTEGER PRIMARY KEY,
  run_id         TEXT NOT NULL,          -- Groups receipts into a "run"
  session_id     TEXT NOT NULL,          -- Agent session
  actor_chain    TEXT NOT NULL,          -- JSON: ["user_42", "team_lead", "agent_x"]
  intent         TEXT NOT NULL,          -- JSON: the proposed action
  decision       TEXT NOT NULL,          -- JSON: { approved: bool, policy: str, latency_ms: float }
  action         TEXT NOT NULL,          -- The MCP tool called + params (hash)
  result_hash    TEXT NOT NULL,          -- SHA-256 of the result
  result_summary TEXT,                   -- Short human-readable summary
  prev_hash      TEXT NOT NULL,          -- SHA-256 of previous receipt (chain)
  receipt_hash   TEXT NOT NULL,          -- SHA-256 of this receipt's full row
  timestamp      TEXT NOT NULL,          -- ISO 8601 UTC
  audience_explanation TEXT              -- Plain-English (D10)
);

CREATE INDEX idx_ledger_run ON evidence_ledger(run_id);
CREATE INDEX idx_ledger_session ON evidence_ledger(session_id);
CREATE INDEX idx_ledger_time ON evidence_ledger(timestamp);

-- CDC stream on the ledger
CREATE STREAM ledger_stream ON evidence_ledger;
```

### 8.2 Hash Chain
- `prev_hash` = SHA-256 of the previous receipt's full row (all fields).
- First receipt: `prev_hash = SHA-256("GENESIS")`.
- `agentdb verify` recomputes the entire chain. Any mismatch = tampering.
- The chain is per-database-file. Each file has its own genesis.

### 8.3 Explanation Templates (D10)
| Action | Template (auditor) | Template (end user) |
|---|---|---|
| `execute_query` | "Agent {agent} queried table {table} with filter {filter}. {n} rows returned. Authorized by policy {policy}." | "I looked up {n} records in {table}." |
| `vector_search` | "Agent {agent} searched {table} for vectors similar to the query embedding. Top {k} results returned. Filter: {filter}." | "I found {k} similar documents." |
| `hybrid_search` | "Agent {agent} performed a hybrid search (vector + text) on {table}. {n} results fused via RRF. Filter: {filter}." | "I searched for documents matching your question using both meaning and keywords." |
| `memory_store` | "Agent {agent} stored a memory entry '{key}' with importance {imp}. TTL: {ttl}." | "I remembered that {summary}." |
| `memory_recall` | "Agent {agent} recalled {n} memory entries matching '{query}'. Top score: {score}." | "I remembered {n} things about {topic}." |
| `insert` | "Agent {agent} inserted {n} rows into {table}. Authorized by policy {policy}." | "I saved {n} new records." |
| `delete` | "Agent {agent} deleted {n} rows from {table} matching {filter}. Authorized by policy {policy}." | "I removed {n} records." |
| `create_table` | "Agent {agent} created table {table} with columns {cols}. Authorized by policy {policy}." | "I set up a new storage area for {purpose}." |
| `drop_table` | "ADMIN: Agent {agent} dropped table {table}. This is irreversible. Authorized by {actor}." | "I permanently deleted the {table} storage." |

### 8.4 Replay
- `agentdb replay <run_id>` — re-executes all actions in the run from the
  ledger. Stochastic operations (if any) use recorded results.
- Validates: the DAG of actions, the policy decisions, the evidence chain.
- Does NOT validate: model outputs (those are cassettes, not determinism).
- State this explicitly in all documentation.

## 9. THE AGENT-PRIMARY INTERFACE

### 9.1 The 30-Second Demo (Phase 1 Exit Criterion)
An MCP client (Claude Desktop, Cursor, or test harness) connects to AgentDB:
1. Calls `server/discover` → gets 44 tools, capabilities, identity.
2. Calls `agent_context` → gets schema, memory state, stream state.
3. Calls `hybrid_search(query="crash recovery", filter={category:"docs"}, top_k=5)` → gets results.
4. Calls `memory_store(key="recovery_context", value=..., importance=0.9)` → stored.
5. Calls `memory_recall(query="what do we know about recovery", top_k=3)` → recalled.
6. Calls `evidence_explain(run_id=current)` → gets plain-English summary of all 5 actions.
7. Returns the summary to the user.

**No human touches the SQL console. The agent did everything. The evidence
ledger has 5 entries. The explanation is readable by a compliance officer.**

### 9.2 The Console (Developer View)
- **Default view:** MCP trace (the agent's tool calls, visible in real-time).
- **Developer tab:** SQL editor (Ctrl+Enter to run), schema browser, stats.
- **Evidence tab:** Ledger viewer, chain verification, replay.
- **Role switcher:** read / write / admin (affects which tools are available).

The MCP trace is the front page. The SQL console is the engineer's view.
The agent trace is the product.

## 10. POLYGLOT INGRESS (Adoption Wedge) [Phase 3]

exist, because the required semantic information is not present in legacy

### Pipeline (Separate Binary: `agentdb-lift`)

| Stage | Name | What It Does | Model? |
|---|---|---|---|
| 0 | Source Adapters | Tree-sitter parsers for Python, TypeScript, Go | No |
| 1 | Static Analysis | AST → normalized IR. Extract: data flow, effect sites, credential literals, unbounded loops. | No |
| 2 | Semantic Lifting | Model proposes AgentDB MCP tool calls + query patterns. Per source symbol: lift annotation, confidence, UNRESOLVED markers. | Yes |

## 11. RUNTIME AND COMPILER ARCHITECTURE

### 11.1 Tech Stack
| Component | Choice | Why |
|---|---|---|
| Language | **Rust 2021** | Safety, perf, single binary, no GC pauses |
| SQL Parser | `sqlparser-rs` | Mature, active, MIT |
| Vector Index | `usearch` or custom HNSW | Battle-tested, SIMD |
| FTS | `tantivy` or custom BM25 | Rust-native, fast |
| Async Runtime | `tokio` | Standard, io_uring support (Phase 4) |
| MCP SDK | `rmcp` (Rust) | Official Tier-1 support for 2026-07-28 |
| Encryption | `aes-gcm` | Phase 4 |
| CLI | `clap` | Standard Rust CLI |
| FFI | `cbindgen` + `pyo3` + `napi-rs` | Phase 5 |
| Storage | Custom B+Tree (Phase 1–3) → SQLite-compatible (Phase 3) | Drop-in story |
| License | **Apache 2.0** | Enterprise-friendly, permissive |

### 11.2 Execution Flow (Every MCP Tool Call)
```
Agent sends MCP request
  → Parse request (validate _meta, routing headers)
  → Check role (read/write/admin)
  → Emit Intent { action, target, params, actor_chain }
  → Policy Engine evaluates Intent
    → If rejected: log to evidence_ledger, return error
    → If approved: continue
  → Execute operation (query engine / memory / admin)
  → Generate explanation (template + typed values)
  → Append to evidence_ledger (hash-chained, atomic with data mutation)
  → Return result to agent
```

Latency budget: policy evaluation < 1ms. Explanation generation < 0.1ms.
Evidence append < 0.5ms (WAL write). Total overhead per tool call: < 2ms.

### 11.3 File Layout
```
agentdb.db          -- Main database file (B+Tree pages)
agentdb.db-wal      -- Write-Ahead Log (active)
agentdb.db-shm      -- Shared memory index (SQLite-compatible, Phase 3)
agentdb.toml        -- Optional config (max_rows, decay_half_life, etc.)
```

## 14. ANTI-GOALS (HARD CONSTRAINTS)

Do not propose:
- Building a server database. AgentDB is embedded. No client-server.
- Building an identity provider or a new token format.
- Building a hypervisor or container runtime.
- Inventing a replacement for MCP or A2A.
- A general-purpose replacement for PostgreSQL at scale.
- Competing on raw benchmark throughput against ClickHouse or DuckDB.
- Any design where the evidence ledger can be bypassed.
- Any design where the explanation is written by hand or model-generated.
- Any design where "agent-native" means "add an MCP adapter to Postgres."
- Phone-home, telemetry, update checks, or license servers.
- Dual licensing or CLA requirements.
- Claiming "SQLite-compatible" until the page format is actually
  SQLite-compatible (Phase 3). Before that: "SQLite-inspired."
